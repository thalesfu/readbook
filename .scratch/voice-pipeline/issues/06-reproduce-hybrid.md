# 06: 在 5090 上复现混合版

Type: prototype（HITL）
Status: resolved
Blocked by: 01, 04, 05

## Question

用 Windows 上的 CUDA 版模型，按混合版配置（定妆音见 `books/wa2/voices/`）重做小样和〈2002〉：
- 指标上能不能达到 Mac 混合版的水平；
- 试听是否同等。

这是后面所有对比的基线。如果复现不了，要先查清差异出在哪个环节。

## Answer

复现成功，可以当基线。

- **用户试听结论**："基本可以算是等同"，整体上 5090 版还要好一些。有问题的句子和 Mac 版在差不多的位置，只是问题更明显。
- **基线文件**：在 `books/wa2/baseline/` 下，07–12 号原型票都和它们比。
  - `小样-混合版-5090.mp3`
  - `2010-11-25 〈2002〉-混合版-5090.mp3`
  - 每份都带 `-对照剧本.md`（时间戳）、`-指标.md`、`-指标-逐句.jsonl`

```
uv run python -m readbook.passage 小样
uv run python -m readbook.passage "2010-11-25 〈2002〉"
uv run python -m readbook.evaluate 小样|2002 <MP3>
```

- `passage` 的产物在 `out/passage/<名字>/`，逐句干声、`qc.json`、MP3、对照剧本都在这里。
- 剧本已经有了，就不再剧本化；第一次做新片段时，再传路线、日期、起始 sid。

**指标**（Mac → 5090，都是从混好的 MP3 切回逐句算的，只算 ≥1.5 秒的句子）：

| | 小样 | 〈2002〉 |
|---|---|---|
| 过音色门槛 | 21/29 → 20/30 | 35/44 → 33/43 |
| 像原声 中位（最低） | 0.56（0.23）→ 0.54（0.23） | 0.54（0.13）→ 0.52（0.23） |
| 像锚点 中位 | 0.79 → 0.76 | 0.63 → 0.60 |
| 认人·锚点 | 26/29 → 28/30 | 36/44 → 40/43 |
| 认人·原声中心 | 27/29 → 29/30 | 40/44 → 41/43 |
| 认人（含短句，锚点 / 原声中心） | 36/43、40/43 → 34/43、39/43 | 44/58、51/58 → 46/58、54/58 |
| 字错率 >0.3 | 4 句 → 2 句 | 3 句 → 2 句 |
| 句内变调 | 4 句 → 2 句 | 0 → 1 句 |

- **〈2002〉分角色**：
  - 雪菜 12/13 → 12/13，像锚点中位 0.77 → 0.77；
  - 春希旁白和心里话 23/31 → 21/30，最低值从 0.13 升到 0.23。
- **小样分角色**：
  - 雪菜 10/10 → 9/10；
  - 依绪 5/7 → 4/8；
  - 春希台词 1/5 → 1/5；
  - 春希·讲述 4/6 → 5/6；
  - 武也 1/1 → 1/1。
- **音高和语速**：大体一致。只有小样里春希台词的音高中位从 141Hz 升到 164Hz（目标 158Hz，P90 从 173Hz 升到 200Hz）。
- **差异的大小**：每句只出一个成品，两三句的差别在随机波动范围内（见下面"跑偏是按句的概率"）。

**合成速度**（5090 笔记本，混合版配置，含重试、CAM++ 和质检，不含加载模型的约 11 秒）：
- 合成耗时约为成品音频的 2.0 倍：小样 297 秒出 146 秒，〈2002〉543 秒出 266 秒。
- 折合每字 0.49 秒，全书 168 万字约 230 小时，也就是 9.6 天，**还没到地图上"一周内"的目标**。
- 单条生成的耗时约为音频时长的 1.7 倍。一批 5 个候选只比单条慢一成左右，显存峰值约 6GB。所以每句的候选一次批量生成。

**做了什么**：
- **`readbook/bakeoff.py`**：
  - 新增 `TorchQwen`：官方 PyTorch 版 Qwen3-TTS-12Hz-1.7B-Base，主模型 bf16、sdpa，不装 flash-attn。
  - 参数逐项对着 mlx-audio 0.6.1 的源码对齐：
    - 非流式布局；
    - 子 talker 和主 talker 同一个温度（0.6）；
    - top_k 50、top_p 1.0；
    - 重复惩罚 1.5、只罚最近 64 个首码本 token：先屏蔽再罚，包一层 `talker.generate` 实现；
    - 语音编码器用 fp32，见下面的排查。
  - 生成上限按句长定，比 `ok()` 的时长上限多 1 秒。
  - 新增 `load_qwen()`、`qwen_takes()`，按平台分支。Mac 上仍然一个一个生成，过了质检就停；Windows 上一批生成，调用方按同样的顺序挑，结果的分布和逐个生成一样。
  - `synth_qc()`、`synth_anchor()` 是从原来的循环里抽出来的，`cmd_synth`、`cmd_synth_anchor` 也改用它们。
- **`readbook/passage.py`**：
  - 定妆音改成从 `books/wa2/voices/voices.yaml` 读，Mac、Windows 共用；
  - 能直接做小样；
  - 依绪、武也改成锚点版：原来写的是 single，〈2002〉里没有这两个人，所以没暴露；
  - `qc.json` 里多记了用的定妆音、每句耗时和成品时长。
- **依赖**：
  - Windows 上加了 `qwen-tts==0.1.1`。它把 transformers 钉在 4.57.3，又要求 huggingface_hub <1.0，所以 Windows 上这两个降到 4.57.3 和 0.36.2；
  - Mac 锁定的版本不变。`pyproject.toml` 里按平台分开写 hub 的范围，uv 才会分开解；
  - 降级后拿 Mac 基线的 MP3 重跑 evaluate，逐句结果完全一致。
- **文档**：`docs/audiobook/` 的运行环境文档、技术报告已更新。

**第一版没复现出来：雪菜音色跑偏，原因是语音编码器的精度**：
- **现象**：第一版主模型和语音编码器都用 bf16。春希反而更好（〈2002〉讲述 29/31），雪菜却明显变差：〈2002〉6/13、像锚点 0.37，小样也有 4 句跑偏。干声也一样，不是混音或切分的问题。
- **跑偏是两极的**：每个候选要么像锚点 0.8–0.9，要么只有 0.2–0.5，像换了个人。
- **四项参数都排除了**：取〈2002〉的 8 句雪菜，每句 10 个候选。重复惩罚换成官方 1.05 全历史、子 talker 温度改成 0.9、改用流式、一条一条地生成，候选跑偏率都在 42–57% 之间，不比现在的做法（50%）好。
- **真正的原因**：`speech_tokenizer/` 的权重存的是 fp32，mlx-community 版也是同一份文件，mlx-audio 加载时不转精度。官方 `from_pretrained(dtype=bf16)` 会把它跟着主模型一起转成 bf16。
- **修正后**：改成 fp32 单独加载，这 8 句的跑偏率从 50% 降到 25%；重做后雪菜回到 Mac 的水平。
- **代价**：速度只慢了约 7%（2.04 倍对 1.90 倍）。

**顺带发现的**：
- **参考码对复刻稳定性影响很大，方向因人而异**。在〈2002〉全部长句上不挑句子地比，每句 5 个候选，看过门槛的比例：

  | | 参考音 bf16 编码 | 参考音 fp32 编码 |
  |---|---|---|
  | 春希·讲述（30 句） | 89%（fp32 解码 93%） | 71% |
  | 雪菜（13 句） | 69%（fp32 解码 71%） | 85% |

  - 解码的精度不影响结果，起作用的是参考音编码出来的码，所以这不是 CAM++ 被骗。
  - 同一段定妆音，参考码只差一点数值误差，复刻就稳定或不稳定得多。
  - 这说明"参考音怎么编码"本身就是一个能调的环节。【推测】可以自动给每个定妆音试几种编码（不同精度、首尾留白、截取），按 CAM++ 门槛挑最稳的一种。这种做法对所有角色一样，不算按人特调，07、08 号票可以试。
- **跑偏是按句的概率**：
  - 跑偏的概率主要由句子本身决定。比如〈2002〉雪菜第 1、5 句，候选十有七八跑偏；第 6、11、14 句几乎不偏。
  - 这和用户听到的"问题句位置和 Mac 差不多"对得上。
  - 每句只取一个成品时，两三句的差别就在随机波动范围内。
- **雪菜靠重试拦不住跑偏**：她用的是不分情绪的单一锚点，配方里没有 CAM++ 门槛，跑偏的候选只要音高、语速合格就会被选中（〈2002〉第 5、8、12、19 句都是第一个候选就过了质检）。依绪、武也的锚点版有逐句门槛，所以稳得多。
- **04 号票验证清单的结果**：
  - 流式和非流式下的音色跑偏率差不多，但没测流式下"越读越快"；
  - 子 talker 温度 0.9 比 0.6 略差（跑偏 57% 对 50%）；
  - 重复惩罚 1.05 全历史和 1.5@64 差不多（42% 对 50%），1.5 全历史没测；
  - batch=1 和 batch=5 的耗时见上面的合成速度。
- **两个 GPU 任务同时跑**会报 `CUDA error: unknown error`，要一个一个跑。

**留给后面的票**：
- **速度**：全书 9.6 天，要压到一周以内。现在只有同一句的候选在批量生成，句子之间是串行的。可以试几句并一批，或者 CUDA graph（见 04 号票调研笔记 §6）。
- **参考码编码的选择**：见上面"顺带发现的"，可以在 07、08 号票里试。
- **小毛病**：evaluate 的"情感 × 音色"表里，句数相同的行顺序不固定（集合迭代顺序），数字不受影响。
